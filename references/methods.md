# 调查方法

按要回答的问题挑选方法。一种方法解释不了现象时，换工具、组合多种方法、自写脚本，或请用户提供具体证据。调查记录的写法见 SKILL.md 第 4 步，证据格式见 ledger.md。

## 按问题选方法

| 要回答的问题 | 可用的方法 | 需要确认的结果 |
| --- | --- | --- |
| 有哪些入口和功能？ | 包结构、Info.plist、AX、GUI、AppleScript 字典、资源文案、帮助文档、版本说明、代码里的事件注册 | 入口能否实际到达，在什么状态下可用，是否只是遗留的旧资源 |
| 一次操作改变了哪些状态？ | 受控输入、前后快照、文件和数据库检查、系统日志、文件访问追踪、函数调用观察 | 前置状态、变化内容、何时写入磁盘、失败和重启后的状态 |
| 算法、格式或默认值是什么？ | 边界输入、差分实验、资源解析、自写解析器；原生 App 在实验定不下规则时，用 REA 的 `open_binary` 打开主程序，按文案、常量或符号定位函数，再看交叉引用和反编译结果 | 输入输出、编码与舍入规则、边界条件；推断出的规则回到 A 上验证 |
| 内部为什么走了不同的路径？ | REA 的 `observe_native_calls` 记录一次运行中实际进入的函数和 Objective-C 方法、参数寄存器和调用栈；需要改参数或单步时，用 LLDB、Frida 和受控重放 | 目标版本、CPU 架构、权限、调用顺序；插桩本身是否改变了 A 的行为 |
| 是否依赖服务端？ | 依赖检查、用测试账号观察网络、把请求响应和本地状态对应起来、对可控服务做协议测试 | 哪些状态在客户端、哪些在服务端；离线行为、认证和错误分支 |
| 视觉或交互为什么不同？ | 实际操作 GUI、录屏或逐帧观察、AX 和视图信息、截图测量、实际拖放和键盘测试 | 窗口尺寸、语言、系统外观、缩放、焦点、动效和原生控件行为 |
| 用什么实现最可靠？ | 系统框架、公开算法、兼容库、原生或跨平台 UI、小型技术验证 | 功能是否真实可用，构建和运行依赖，可维护性，与 A 的差异 |
| B 的行为是否已经一致？ | A/B 同输入差分、自动化和 GUI 回归、边界输入和变形测试、用户试用 | 可见结果和副作用都一致；预期结果来自 A |

## 按技术栈调整

- **原生 App**：按需检查 Mach-O、Objective-C/Swift 元数据、链接库、nib/storyboard、资源、Helper 和 XPC。REA 的反编译需要 Hopper、Ghidra 或 IDA 作为 provider，`binary_session` 列出当前可用的 provider 和工具；也可以直接使用合适的反编译器和调试器。Swift（尤其是 SwiftUI）的反编译结果难读，围绕具体问题逐个函数查看。`observe_native_calls` 会真正启动 A，带 hardened runtime 的 A 需要 `get-task-allow`，按下文「插桩和修改副本」在副本上处理。
- **Electron App**：REA 是读代码的主要工具。以 SKILL.md 第 3 步 `analyze_javascript_application` 的结果为代码地图，调查单个功能时用 `trace_application_feature`，从界面文案、IPC 通道、模块或 API 追到实现。
- **WebView、Qt 等其他跨平台 App**：检查实际的包结构、资源、脚本、模块和事件注册，使用该技术栈适用的解析和运行时工具。从 Electron 和这类 App 提取出的代码只作分析材料：功能仍要在 A 上验证，放进 B 前要确认有再分发依据。
- **文件、音视频、图像和开发工具类 App**：先识别格式、算法和现成可用的组件，用小规模的输入输出实验确认兼容性。成熟的基础组件直接复用公开库和系统能力，固定依赖版本并保存许可信息。

## 扩展能力

安装新工具前，确认现有工具确实不够用。第三方脚本先读内容再运行。新工具失败时，在 `progress.md` 记下错误和替代方案，换一种方法继续。

## 插桩和修改副本

- 调试、插桩、重签名或打补丁可能受代码签名、系统保护和 CPU 架构限制，先确认有权限、且是受支持的做法。
- 修改在 A 的副本上进行，记录改了什么；修改过的副本和原版 A 分开命名。
- 从修改副本得到的结论，最后在未修改的 A 上复核外部行为。
- 只读取与 A 相关的数据。需要更改系统安全设置时，按 SKILL.md 先取得授权。

## 使用子 Agent

可以让子 Agent 分别调查不同功能区、实现不同模块或执行测试。开始前约定好共享的功能 ID、证据目录和接口；同一时间只让一个子 Agent 修改 A 的同一份状态或同一个源文件。合并后由主 Agent 重新验证子 Agent 的结论和代码。
